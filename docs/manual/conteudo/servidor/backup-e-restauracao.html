Para que serve

Se o servidor quebrar, for apagado por engano ou deixar de existir, os seus clientes, conversas, negócios e arquivos só voltam se houver uma cópia. A instalação do ZapSales já agenda as cópias sozinha. Esta página explica o que é guardado, onde, por quanto tempo, e como conferir que a cópia realmente serve — uma cópia que nunca foi testada não é garantia.

A cópia diária fica na própria VPS.

Ela protege contra erro (apagar algo sem querer, uma atualização que deu errado), mas não protege contra perder a máquina. Para isso existe a cópia semanal fora do servidor, descrita abaixo — que você precisa ligar uma vez.

As duas camadas de cópia

CamadaQuandoO que guardaOnde ficaPor quanto tempo
Cópia diáriaTodo dia às 03:15 (hora da VPS)O banco de dados inteiro, mais a contagem de linhas que ele contém (usada para conferir a restauração)No próprio servidor, em /var/backups/zapsales/db/30 dias
Cópia semanalTodo domingo às 04:30Uma cópia nova do banco, as mídias (imagens, áudios e arquivos), as sessões do WhatsApp, as mídias do WhatsApp e o arquivo .envFora do servidor, no Cloudflare R2, criptografada8 semanais e 6 mensais

As duas são agendadas pela instalação em /etc/cron.d/zapsales. O registro de cada rodada fica em /var/log/zapsales/backup.log.

Por que o arquivo .env entra na cópia

O .env guarda as chaves que trancam dados dentro do banco: CPF, chaves de IA e credenciais de integrações. Um banco restaurado sem o .env que o acompanhava volta com essas informações ilegíveis. Por isso a cópia semanal é criptografada inteira, e por isso você precisa guardar a senha dela (veja abaixo).

Os comandos do dia a dia

Todos rodam no terminal do servidor, com sudo, a partir de /opt/zapsales:

ComandoO que faz
kit/backup.sh statusMostra os últimos dumps, a última cópia semanal e se o R2 está configurado. É o primeiro a rodar para saber se está tudo certo.
kit/backup.sh diarioFaz a cópia diária agora.
kit/backup.sh semanalFaz a cópia semanal para o R2 agora.
kit/backup.sh listarLista as cópias guardadas no R2.
kit/backup.sh configurar-r2Grava as credenciais do R2 (uma vez só).

Ligar a cópia fora do servidor (Cloudflare R2)

O R2 é o armazenamento da Cloudflare. Você faz isto uma vez:

  1. No painel da Cloudflare: R2 › Create bucket (por exemplo, zapsales-backup).
  2. R2 › Manage API tokens › Create API token, com a permissão Object Read & Write, restrita a esse bucket. Anote o Access Key ID, o Secret Access Key e o Account ID (que aparece na URL e na página do R2).
  3. No servidor, rode sudo /opt/zapsales/kit/backup.sh configurar-r2. Ele pergunta os quatro valores (conta, bucket, chave de acesso e chave secreta), gera a senha de criptografia, grava tudo em /etc/zapsales/backup.env (que só o root lê) e prepara o repositório.
  4. Guarde a senha de criptografia fora do servidor, no seu gerenciador de senhas: sudo grep RESTIC_PASSWORD /etc/zapsales/backup.env.
Sem a senha do restic, a cópia não abre.

Se você perder a VPS e não tiver essa senha guardada em outro lugar, a cópia semanal fica impossível de abrir. Ela não existe em nenhum outro lugar além do arquivo /etc/zapsales/backup.env do próprio servidor. Guarde-a hoje, antes de precisar.

Testar a restauração todo mês (o “ensaio”)

O ensaio não toca no que está no ar. Rode:

sudo /opt/zapsales/kit/restaurar.sh ensaio

Ele baixa a cópia semanal mais recente do R2 e monta um ambiente separado na mesma VPS (outro projeto do Compose chamado zapsales-ensaio, outros volumes, outra porta interna — a padrão é a 18088 — e sem entrada no proxy). Ele:

  1. sobe um banco novo, aplica a estrutura do sistema e restaura os dados;
  2. devolve as mídias;
  3. sobe só o aplicativo e o proxy — nunca o worker, o agendador ou o WhatsApp, porque com o banco restaurado eles repetiriam campanhas e follow-ups para clientes reais, e o WhatsApp disputaria o número com o de produção;
  4. confere a contagem de linhas de cada tabela importante (usuários, organizações, contatos, conversas, mensagens, negócios, arquivos) contra a contagem gravada dentro da própria cópia;
  5. prova que o aplicativo abre (código 307) e que o login responde. Com as variáveis ZAPSALES_TESTE_EMAIL e ZAPSALES_TESTE_SENHA, entra de verdade com uma conta.

Para ver o ensaio no navegador, abra um túnel pelo seu computador (ssh -L 18088:127.0.0.1:18088 root@IP-DA-VPS) e acesse http://localhost:18088. Ao terminar, remova o ensaio:

sudo /opt/zapsales/kit/restaurar.sh ensaio --remover

Se a VPS foi perdida (desastre)

Numa VPS nova, com o código em /opt/zapsales e o endereço (DNS) já apontando para ela. O kit instala o Docker se faltar e, numa VPS nova sem nada nas portas 80 e 443, sobe o próprio proxy com HTTPS (veja Instalar o ZapSales numa VPS). Os dois comandos:

  1. Informar as credenciais do R2 e a mesma senha de criptografia guardada: sudo RESTIC_PASSWORD='<a senha guardada>' /opt/zapsales/kit/backup.sh configurar-r2
  2. Restaurar tudo: sudo /opt/zapsales/kit/restaurar.sh desastre

O modo desastre restaura na pasta do kit (o .env original, com o mesmo domínio), devolve o banco, as mídias e as sessões do WhatsApp, confere as contagens e chama o instalador, que configura o proxy e os backups. Ele se recusa a rodar onde já existe um .env — numa instalação viva, use o ensaio.

Este caminho ainda não foi executado de ponta a ponta.

Segundo o próprio projeto, o ensaio exercita a mesma restauração de banco e de mídias, mas a troca de máquina (o modo desastre numa VPS nova) ainda não foi testada inteira. Faça o ensaio regularmente e não confie só nesta etapa. Se a instalação perdida era do tipo “convivendo com outros apps”, o .env do backup traz esse modo: suba antes o Caddy ou o Nginx do sistema na VPS nova, ou rode o passo final com ZAPSALES_MODO=limpa para o ZapSales ficar com as portas.

Só o banco, a partir de uma cópia diária

As cópias diárias não saem da VPS; servem para voltar o banco no tempo (um erro de operação), não para perder a máquina. O caminho é o mesmo do ensaio: um banco novo, a estrutura e os dados da cópia. Faça antes um ensaio com a cópia do R2 para conferir o procedimento.

Uma rotina simples

  • Uma vez: ligar o R2 e guardar a senha de criptografia fora do servidor.
  • Toda semana: rodar sudo /opt/zapsales/kit/backup.sh status e conferir que a última cópia semanal é recente.
  • Todo mês: fazer o ensaio de restauração e remover o ambiente depois.
  • Antes de qualquer coisa que apague dados (como docker compose down -v): conferir que existe uma cópia boa.
